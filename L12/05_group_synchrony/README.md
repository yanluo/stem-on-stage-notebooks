# Project 5 — Group synchrony

> **Score how synchronized two (or more) dancers are over the course of a routine.**

## What's in here

- [`synchrony_starter.ipynb`](synchrony_starter.ipynb) — load two paired recordings → plot together → Pearson correlation → windowed correlation → cross-correlation lag.
- [`wearable_dancer.py`](wearable_dancer.py) — MakeCode Python for each dancer's micro:bit. Reads accelerometer at 20 Hz, broadcasts magnitude on radio group 7 as `magA` or `magB`.
- [`wearable_synchrony.py`](wearable_synchrony.py) — MakeCode Python for the "judge" board. Receives both streams, computes Pearson correlation every 1 s with running sums (no numpy needed), broadcasts `color:green/yellow/red` to the lanterns.
- [`../../data/sample-pair-A.csv`](../../data/sample-pair-A.csv) and [`sample-pair-B.csv`](../../data/sample-pair-B.csv) — two 30 s recordings of the same routine. B lags A by 150 ms during the middle 12 s.
- Generated by [`generate_sample_pair.py`](../../data/generate_sample_pair.py).

## Why this project is special

Every other project measures *one dancer*. This one measures the *ensemble*. Coaches care a lot about ensemble timing, and there's no commercial product that gives them a quantitative answer — you'd be building one.

## Hardware reality check

**Two simultaneous captures = two micro:bits.** No way around it. Three options for L13–L15:

1. **Two students record simultaneously.** Both wear the L11 datalogger, both press A at the same moment (or use a clap-synced start). This is the real path.
2. **One student records twice.** Same routine, twice in a row. Still produces two traces, but they aren't *truly* synchronized — useful only for testing the analysis code.
3. **Develop on the bundled CSVs.** Use sample-pair-A/B to build all the analysis. Only do paired captures once for the final demo.

Path 3 is fine for the first week of L13. Don't gate development on coordinating two students.

## What you need

- 2× micro:bit v2 + 2× battery packs + 2× armbands (for real captures).
- A laptop with Colab access.

## Live lantern feedback: two architectures

The notebook computes synchrony in Colab, where numpy and scipy are free. To put a live score on stage you need to bridge from "Python on a laptop" to "lights on the dancers." Two paths:

### Architecture A — laptop bridge (development & rehearsal)

```
[dancer A] --radio--> [logger] --USB--> [laptop running Python (the notebook code)]
[dancer B] --radio-->                                 |
                                                      v
                                  laptop computes r every 1 s, sends "color:..."
                                                      |
[lanterns] <--radio-- [controller] <--USB-- (back through the logger)
```

The laptop holds the numpy/scipy pipeline — your correlation logic is **identical** to what's in the synchrony notebook. Best for L13 development: iterate on the math in seconds.

**Cost:** a laptop on or near the stage, USB cables.

### Architecture B — fully on-device (the showcase version)

```
[dancer A wearable] --radio "magA" 20 Hz-->
                                              [judge board]
[dancer B wearable] --radio "magB" 20 Hz-->         |
                                              computes r every 1 s
                                              broadcasts "color:..."
                                                      |
                                                      v
                                                [lanterns]
```

Three boards plus the lanterns, no laptop. The trick is that **Pearson correlation has a closed-form expression**:

```
r = (N·Σxy − Σx·Σy) / sqrt[(N·Σx² − (Σx)²) · (N·Σy² − (Σy)²)]
```

Five running sums and one square root — all in MakeCode's `math` library. See [`wearable_synchrony.py`](wearable_synchrony.py) for the implementation.

**Wiring:**
1. Flash [`wearable_dancer.py`](wearable_dancer.py) onto each dancer's board. **Set `ROLE = "A"` on one and `ROLE = "B"` on the other before flashing each.** The board shows its letter at startup so you can tell them apart.
2. Flash [`wearable_synchrony.py`](wearable_synchrony.py) onto a third "judge" board. It shows `J` at startup.
3. The judge starts displaying an icon as soon as it has enough samples: ✓ for green (synced), `?` for yellow (drifting), ✗ for red (way off).
4. The judge also broadcasts `radio.send_string("color:green")` etc. on group 7. Wire those into the L7 lantern controller's existing `on_received_string` handler.

## What to build next (pick one as your L13 goal)

1. **Real paired capture** — two students, same routine, post-hoc clock alignment using a clap visible in both `mag` traces.
2. **Three or more dancers** — average pairwise correlation = ensemble score. Extend the judge to maintain N buffers.
3. **Live lantern feedback** — get **Architecture B** above end-to-end on three boards, then wire it into the lantern controller. The starter wearables are the foundation.
4. **Per-move synchrony** — combine with L11 labels to find which moves the group nails and which fall apart.
5. **Rehearsal scorecard** — track ensemble score across sessions over weeks (laptop bridge logs scores to a CSV).

## Pitfalls and gotchas

- **Clock alignment is the silent killer.** If the two recordings start 200 ms apart, your "synchrony score" is measuring that, not the dancers. The clap-sync trick: at the start of every recording session both dancers clap once together. The clap shows as a clean spike in both magnitude traces; align the spikes in the notebook before doing anything else. (Architecture B avoids this by running everything live, but radio packets still arrive with ~50 ms jitter.)
- **Window size matters.** Too short (<0.5 s) and the windows are too noisy. Too long (>3 s) and you average across moves you wanted to study separately. 1 s is a reasonable starting point.
- **Pearson correlation can lie when both dancers are still.** Both signals are mostly noise → correlation bounces randomly. The notebook handles this with `if std > 1`; the on-device judge handles it via `varA <= 0 or varB <= 0` returning `None`, which leaves the lantern color unchanged.
- **Radio packet loss.** micro:bit radio occasionally drops packets. The judge buffers don't time-stamp samples, so a brief outage from one dancer means the next correlation window mixes A's old samples with B's new samples. Acceptable for a starter; for a real performance, add a sequence number per packet and discard unmatched ones.
